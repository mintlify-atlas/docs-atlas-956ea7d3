Exogenous variables (also called covariates or features) are inputs to a forecast that are known in advance over the entire forecast horizon — for example, a holiday calendar, scheduled prices, or weather forecasts. FoundationForecast supports **future-known dynamic covariates** on a subset of checkpoints, with a consistent data API that works across `forecast()` and `cross_validation()`.

## What counts as a supported covariate

Only **future-known dynamic** covariates are supported in the current iteration. This means features whose value you know ahead of time for every horizon step — price schedules, promotional flags, calendar events, and so on. Static series-level features (e.g. category metadata) and past-only features (e.g. lagged targets) are not part of this API.

## Data API

<CardGroup cols={2}>
  <Card title="df — history + exog" icon="table">
    Your main DataFrame. Alongside `unique_id`, `ds`, and `y`, include one column per exogenous variable covering the **observed** (history) period.
  </Card>
  <Card title="X_df — horizon exog (forecast only)" icon="calendar-days">
    A separate DataFrame with `unique_id`, `ds`, and the same exog columns covering the **next `h` steps**. No `y` column. Used by `forecast()` only.
  </Card>
</CardGroup>

| Argument | Used by | Contains |
|----------|---------|----------|
| `df` | `forecast()`, `cross_validation()` | `unique_id`, `ds`, `y`, exog columns (history) |
| `X_df` | `forecast()` only | `unique_id`, `ds`, exog columns for the next `h` steps (no `y`) |
| `futr_exog_list` | both | Optional list of exog column names; inferred from `X_df` (or `df`) if omitted |

For **`cross_validation()`**, include exog values through the end of each holdout window directly in `df`. The library slices the correct horizon rows from `df` internally — no separate `X_df` is needed.

## The `exog_strategy` constructor parameter

Set `exog_strategy` on a model instance to control how it handles exogenous inputs:

| Value | Behaviour |
|-------|-----------|
| `"auto"` (default) | Use native exog when the checkpoint supports it; raise `ValueError` if `X_df` is provided but not supported |
| `False` | Ignore `X_df` / `futr_exog_list`; run a pure univariate forecast (also in cross-validation) |

<Warning>
  When `exog_strategy="auto"` (the default) and you pass `X_df` to a model whose checkpoint does **not** support native exog, FoundationForecast raises a `ValueError` before any inference runs. For mixed-model runs where some models can't use exog, set `exog_strategy=False` on those models.
</Warning>

## Native exog support by checkpoint

FoundationForecast checks `supports_native_futr_exog()` on each forecaster — a function of the `repo_id` or API model id you configure.

| Model wrapper | Checkpoint pattern | Native exog |
|---------------|--------------------|-------------|
| **Chronos** | `repo_id` contains `chronos-2` (e.g. `amazon/chronos-2`) | ✅ Yes |
| **TimesFM** | `repo_id` contains `3.0` (e.g. `google/timesfm-3.0-pytorch`) | ✅ Yes |
| **TimeGPT** | any `model=` id (e.g. `timegpt-1`, `timegpt-2`) | ✅ Yes |
| **T0** | `theforecastingcompany/t0-alpha` or `t0-beta` | ✅ Yes |
| **TiRex** | `NX-AI/TiRex-2` or any `TiRex-2-*` checkpoint | ✅ Yes |
| **FlowState** | any | ❌ Use `exog_strategy=False` |
| **Moirai** | any | ❌ Use `exog_strategy=False` |
| **PatchTST-FM** | any | ❌ Use `exog_strategy=False` |
| **Sundial** | any | ❌ Use `exog_strategy=False` |
| **TabPFN** | any | ❌ Use `exog_strategy=False` |
| **Tafsut** | any | ❌ Use `exog_strategy=False` |
| **Toto** | any | ❌ Use `exog_strategy=False` |

<Note>
  Other Chronos checkpoints (e.g. `amazon/chronos-bolt-tiny`) and other TimesFM versions (`1.0`, `2.0`, `2.5`) do **not** support exog — passing `X_df` with those checkpoints will raise an error under the default `exog_strategy="auto"`.
</Note>

## Single-model forecast with exog

The cleanest use case: one supported model, `X_df` covering the horizon.

```python
import pandas as pd
from foundationforecast import FoundationForecast
from foundationforecast.models import Chronos, TimesFM

DATA = "https://timecopilot.s3.amazonaws.com/public/data/electricity_price"
df = pd.read_parquet(f"{DATA}/train.parquet")
X_df = pd.read_parquet(f"{DATA}/futr_exog.parquet")

ff = FoundationForecast(
    models=[
        Chronos(repo_id="amazon/chronos-2", alias="Chronos-2"),
        TimesFM(repo_id="google/timesfm-3.0-pytorch", alias="TimesFM-3"),
    ]
)

fcst_df = ff.forecast(df=df, h=24, X_df=X_df, level=[90])
```

Both `Chronos-2` and `TimesFM-3` will receive the future covariates from `X_df`. The output DataFrame contains a point forecast and `lo-90` / `hi-90` columns for each model.

## Mixed-model run with `exog_strategy=False`

When running multiple models where some don't support exog, set `exog_strategy=False` on non-exog models so they silently ignore `X_df` and run univariate forecasts. FoundationForecast validates each model's strategy before dispatching:

```python
from foundationforecast.models import Chronos, Tafsut
from foundationforecast import FoundationForecast

ff = FoundationForecast(
    models=[
        Chronos(repo_id="amazon/chronos-2", alias="Chronos-2"),
        Tafsut(alias="Tafsut", exog_strategy=False),
    ]
)

fcst_panel = ff.forecast(df=df, h=24, X_df=X_df)
```

`Chronos-2` uses the covariates in `X_df`; `Tafsut` ignores them and produces a univariate forecast. Both aliases appear in the output DataFrame.

## Cross-validation with exog

For cross-validation, include exog columns in `df` through the end of every holdout window. The library extracts the correct horizon slice from `df` for each fold automatically.

```python
# df includes exog columns through the full date range (history + holdout windows)
cv_df = ff.cross_validation(df=df, h=24, freq="H", n_windows=3)
```

To explicitly specify which columns are exogenous:

```python
cv_df = ff.cross_validation(
    df=df,
    h=24,
    freq="H",
    n_windows=3,
    futr_exog_list=["holiday_flag", "ex_1", "ex_2"],
)
```

<Tip>
  For models with `exog_strategy=False`, exog columns in `df` are silently ignored during cross-validation — you don't need a separate DataFrame for univariate models in a mixed-model run.
</Tip>

## `futr_exog_list` — optional but explicit

`futr_exog_list` is an optional list of column names identifying which columns in `df` (or `X_df`) are exogenous:

- In `forecast()`: inferred from `X_df` columns (excluding `unique_id` and `ds`) if omitted.
- In `cross_validation()`: inferred from non-target columns in `df` (excluding `unique_id`, `ds`, `y`) if omitted.

Pass it explicitly when your `df` contains derived or helper columns that should **not** be treated as covariates:

```python
fcst_df = ff.forecast(
    df=df,
    h=24,
    X_df=X_df,
    futr_exog_list=["holiday_flag", "price_index"],
)
```

## Validating exog coverage

Before calling `forecast()`, verify that `X_df` contains the correct number of horizon rows — exactly `h` rows per `unique_id`:

```python
# Sanity check: each series must have exactly h rows in X_df
counts = X_df.groupby("unique_id").size()
assert (counts == 24).all(), f"X_df row counts: {counts.to_dict()}"
```

If `X_df` is missing horizon rows for any series, the model will raise an error during inference.
